# Product specification

What to build next and when it is done. Written 2026-11-27. Owner decisions of 2026-11-27 are included.

## 1. Purpose and how to use this file

- Each feature has an ID (`CAT-01`), its behaviour, its status today, where it lives, when it is done, its size and what it needs first.
- Status: **Have** (built, cited), **Partial** (some of it built, the rest stated), **Missing**. "unverified" means the claim was not checked in the code.
- Size: S ≤ 1 day, M a few days, L a week or more.
- Target: the same capabilities as OpenRouter (choosing a model, buying credits, charging, activity and logs, keys, playground, settings), in Lemru's own design, brand and words. Behaviour is copied. The look, the name and the wording are not. Our edge: the data policy (regions, retention, training) and two deployments (Saudi providers only; Saudi and global providers).
- Sources: `STATE.md`, `PLAN.md`, `adr/`, `openrouter-comparison.md`, `research/openrouter-api-parity.md` (field-level gaps, cited below as "parity"), `research/openrouter/openrouter-flows.md` and its screenshots (cited as "flows").

Rules for every feature:

1. **Modular monolith** (`AGENTS.md`): logic and tests in `packages/api/src/modules/<feature>`, tables in `packages/db/src/schema/<feature>.ts`, screens in `apps/web/src/modules/<feature>` (pages in `apps/web/src/app/[locale]`), engine work in `apps/gateway/plugins/<name>`. No module reaches into another module's internals.
2. **Gateway first:** before writing any gateway, money, usage, limit, logging or provider logic, search `apps/gateway` (core, framework, plugins, transports), say what you found and use it. Write our own code only for what it does not do. Every change to an upstream file goes in `apps/gateway/MODIFICATIONS.md`.
3. **Every rule gets a test**, and you prove the test by breaking the rule once and watching it fail. Check each screen in a browser on the production build.
4. **Both products move together:** a product-level change is made in the gateway and the control plane in the same piece of work.
5. **Update this file** when a feature ships: set its status, cite the files and update `STATE.md`.
6. **No hard-coded business values** (owner, 2026-11-27). Anything staff may change (the payment gateway and its mode, fees, top-up amounts and limits, the exchange rate, providers and their keys, prices and price overrides per provider and per key, limits, thresholds, feature switches) is managed in the admin (`apps/web/src/modules/admin`, `packages/api/src/modules/admin`). It is stored in the database, has a safe default seeded by a migration, and every change is written to the admin audit log with who, when, before and after. Code and the gateway read it at runtime (cached for at most 30 s where needed, as `plugins/credits/markups.go` does today) and a change never needs a code edit or a redeploy. Secrets and infrastructure (database URLs, API secrets, signing keys, hosts) stay in env; the admin may refer to a secret by name but never stores or shows its value. Bounds against typos (for example `MAX_TOPUP_FEE_BPS`, `packages/db/src/schema/pricing.ts:24`) and product invariants that are not business choices (content is never stored, ADR 0014; unknown terms count as the worst case, ADR 0015) stay in code. What is hard-coded today is listed in Appendix A, each with the ADMIN feature that moves it.

## 6. Glossary

| Term                    | Meaning                                                                                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Hold (reserve)          | Before an attempt reaches a provider, `plugins/credits` sets aside its worst-case cost from the balance (`credit_reservation`) |
| Settle                  | After the attempt, the real cost is written to the ledger once and the hold is released                                        |
| Virtual key             | The gateway's key; each dashboard API key is one virtual key (ADR 0004)                                                        |
| Customer / organization | An organization in our app is one customer in the gateway; it holds the balance, the keys and the policy                       |
| Provider endpoint       | One provider key in the gateway, with its data terms (region, retention, training) in `provider_endpoint`                      |
| Upstream attempt        | One call to one provider endpoint; a request with fallback has several, each logged and settled on its own                     |
| Upstream cost           | What the provider charges for an attempt, in USD; shown to the customer                                                        |
| Data policy             | An organization's rules on where its requests may go: zero retention, no training, regions, providers (ADR 0015)               |
